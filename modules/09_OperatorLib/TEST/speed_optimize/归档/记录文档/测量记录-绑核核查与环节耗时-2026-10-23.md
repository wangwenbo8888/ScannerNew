## 一、CPU 物理核心分配核查（问题①）

### 1.1 拓扑与实际落位（i7-9850H，6C/12T，相邻配对）

物理核→逻辑核：核0=[0,1] 核1=[2,3] 核2=[4,5] 核3=[6,7] 核4=[8,9] 核5=[10,11]。
代码经 `GetLogicalProcessorInformation` 动态查询后绑核（`fc_executor.cpp:32-97`），
**映射本身无 bug**。落位：

| 物理核 | 逻辑核 | 线程 | 稳态利用率（均值/峰值） |
|---|---|---|---|
| 核0 | LP0 | 系统保留（不绑） | 29% / 55% |
| 核0 | LP1 | 空（ch2 备选位） | **11%** / 55% |
| 核1 | LP0 | 读帧＋预上传（1a） | 22% / 70% |
| 核2 | LP0 | GPU 喂料（1b） | **78%** / 100% |
| 核2 | LP1 | **ch2 激光后段（默认位）** | **54%** / 100% |
| 核3/4/5 | LP0 | 标记链×3 | 32/32/41% / ≤85% |
| 核1/3/4/5 | LP1 | 浮动（fuse/reg 等） | 14-18% / ≤69% |

（PDH 逐逻辑核 100ms 采样 ×735 行，按「多链同活」特征过滤出 43 个稳态行；
采样脚本 `C:\Users\DUUMM\AppData\Local\Temp\opencode\lp_sampler.ps1`。）

### 1.2 发现：ch2 挤错位置——设计假设已过时

- 绑核依据的注释（`fc_executor.cpp:871`）：「1b 是 GPU 等待型线程，活跃段
  ~0.5ms/帧」→ **实测 1b 是全流水线最忙 CPU 线程（78% 均值）**——WDDM 下
  每帧 ~64 次任务提交的 CPU 税远超当年估的 0.5ms。
- 后果：ch2（54% 重活）与最忙的 1b 挤同一物理核互抢；核0-LP1（11% 占用）
  反而闲置。

### 1.3 ABBA 实测（各两轮 399 帧，全部同配方）

| 实验 | e2e 中位 | wallCh2 | FPS |
|---|---|---|---|
| ch2 默认位（核2-LP1，与 1b 同核） | 7533 / 7540 | 5165 / 5012 | 132.7 / 132.6 |
| **ch2 备选位（核0-LP1）** `JMW_FCPIN_CH2=0` | **7423 / 7429** | **4498 / 4547** | **134.7 / 134.6** |
| 绑核优化版（ch2@核0） | 7493 / 7434 | 4378 / 4480 | 133.5 / 134.5 |
| 完全不绑核 `JMW_AFFINITY=0` | 7625 / 8018 | 4549 / 4506 | 131.1 / **124.7** |

结论：
1. **ch2 移备选位：wallCh2 −11%、e2e −0.11ms、+2 FPS**——两对重复全部一致
2. **绑核体系整体有价值**：不绑核慢 ~5% 且方差大（一轮掉到 124.7，浮动线程
   被本机 VS Code/opencode 挤）
3. **建议一行修复**：`fc_executor.cpp:876` 默认 site `2`→`0`（连带更新 :871 注释
   的过时假设）；落地前性能跑批用 `JMW_FCPIN_CH2=0` 应急

## 一·补、标记链 lanes 数核查（3 → 2 够不够，2026-10-23 深夜追加）

**问题**：标记链 ×3 条各绑核3/4/5，实测仅 32-41% 占用——2 条是否够？

**ABBA 四轮**（config_flat+ALL_raw+OCV0+ch2@核0；markerLanes 经临时配置副本
设 2，仓库 config 未动；本段期间机器噪声带偏宽 125-134 FPS）：

| 方案 | e2e 中位（两轮） | wallMk 中位 | wallMk P90 | tomb/trunc |
|---|---|---|---|---|
| 3 lanes | 7851 / 7459 | 5065 / 4505 | 11628 / 10229 | 0 / 0 |
| 2 lanes | 7817 / 8003 | 4490 / 4678 | 11070 / 10713 | 0 / 0 |

**结论**：
1. **2 条够用**：吞吐容量 ≈ 1 帧/2.3ms（wallMk 4.5ms÷2），对 7.5ms 到达率有
   3 倍余量；P90 尖峰帧 11ms 时容量 1 帧/5.5ms 仍高于到达率；实测帧率/尾巴
   与 3 lanes 差异在噪声带内；功能零异常（帧全处理、无墓碑无截断）
2. **但省不出白捡的好处**：核5 腾出来后当前无人使用——ch2 绑核位硬编码只有
   核0/核2 两选一（`fc_executor.cpp:877` 三目），要给 ch2/fuse 独占核5 须改代码
3. **建议**：默认暂保 3 lanes（余量抗后台干扰/抗未来负载变化更稳）；若做
   「ch2 绑核任意化」小改动（连同 §1.3 的默认位翻转一起），2 lanes+ch2 独占
   核5 的组合才值得上——列为可选小刀，非必需

### 2.4 结构性观察（给后续决策）

- **GPU 喂料线程（1b）78% CPU 是主机侧最大单点**：WDDM 提交税。降它的 CPU
  需减少发射次数或改 Linux/TCC——前者「图打包/减递单」已证伪，环境换道是
  唯一彻底解（档案在案）。#2 拆分不减排发射但移走同步，属可做部分。
- 标记链三 lane 仅 32-41% 负载：GPU 侧若降至 ~5ms，现有标记链容量（~6ms 摊薄
  后）接得住，无须加 lane。
- 兑现率教训仍然有效（10-22 §八）：#3/#4/#5/#6 的 GPU 计算节省在 #2 落地前
  大概率不转化为帧率——它们的价值顺序是「先 #0/#1/#2 拿端到端，再 #3-#6
  降功耗腾余量」。
