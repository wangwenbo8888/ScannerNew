## 三、性能病理（正确但慢——K2 v1 中位 6-8ms vs 宿主 c7casc 0.10-0.15ms）

相位隔离（sparse_30 中位 k2ev）：**轮框架 0.36ms ✓ / 淘汰段 ≈4.2ms ✗ / 安全检查 ≈6.8ms ✗（主犯）**。

根因：**单块＝单 SM，淘汰/安全检查两段的行位图与 CSR 访问是 L2 延迟受限负载**——16 warp 藏不住 ~250ns 延迟；安全检查的逐对串行归并游走尤其重（每步 6 次相关 L2 载入）。512/1024 线程无差异（排除寄存器溢出主因）。与第四/五轮审核"单块 L2 驻留退化"警告吻合，量化坐实。

## 四、K2 v2 设计方向（下会话实施）

1. **安全检查重设计（主犯 6.8ms）**：
   - 首选：**每单元行均值预计算**（rowXSum/rowCnt → rowMean，一次并行除法 ΣR~万元素）＋ 对内改"**位图 AND 逐字并行**＋每共享行二分查找"——消除逐对串行游走的延迟链；归并序＝行升序仍可保逐位（预计算均值改变除法时机，宿主同改对照或走容差——需对拍裁决）；
   - 备选：宿主混合（GPU 轮＋宿主检查＋回传 banned 重跑）——iters 中位 1.2，同步代价可控；
2. **淘汰重设计（4.2ms）**：**倒排行→单元索引**（每 iter 一次并行构建，Σ 条目 ~1.5 万）——每轮淘汰只扫 best 的稀疏行×在扬单元，替代 U×128 盲扫；
3. **保留**：票表驻 shared 的轮框架（0.36ms 实证健康）、U>128/250 轮回退、幂等写确定性、oracle 对拍口径。

## 五、本会话坑与工具

- `$Matches` 只被 `-match` 填充（Select-String 不填）——第 3 次踩，已立规矩：解析一律 `ReadAllLines`＋`-match` 落脚本文件；
- ncu 计数器被驱动策略锁（ERR_NVGPUCTRPERM，无管理员权限不可用）——性能剖析以**相位隔离开关**替代（本会话发明，效果良好）；
- 1024→512 线程对延迟受限负载无效（平行度不是瓶颈，延迟才是）。

## 十、K1b 实施指引（下一工作块直接开工用）

**目标**：友军合并 GPU 化（宿主 c7merge 0.82-1.32ms → GPU ~0.1ms），同时解锁 K1a 净收益（盖章 CSR 停止下载、留设备侧直喂）。

**形态（原子版裁定）**：
1. 均值稠密化：kernelSegMeanScatter——把盖章 CSR（d_grp_sum/cnt，已有）散建到 dense [512][8192] double（33MB，grow-once；仅写在场行无需清零）；
2. 行桶转置：kernelRowBuckets——扫 segRows 位图（s,w）并行，每置位行 r：atomicAdd 计数＋散置 s 入 per-row 段列表（CSR：rowOff[8193]＋segList[Σ]，Σ=ΣR 预算 ~40 万内）；
3. 对贡献散布：kernelPairScatter——每行 r，段列表内两两 (s<t)：atomicAdd(pairSum[s*512+t], fabs(dense[s][r]-dense[t][r]))、atomicAdd(pairN, 1)——Σk2 线程量（G-1 实测 10^5-10^6）吞吐形态；
4. 宿主收尾（留宿主＝裁决归属同款理由）：下载 pairSum/pairN 实际 S2（~85KB@S=73）＋门限判定＋并查集（~0.05ms）——复用 cascadeSolve 现有 gpuPairSum/gpuPairN 直取参数（刀③接口现成！）；
5. 挂接：刀③槽位（现仅 v3GpuOn）扩为 fullGpuMode_>=1 也走新内核组（旧 kernelPairMergeV3 保留 JMW_V3GPU 兼容）；stamps 下载在 K1b 激活时跳过（数据留设备）。

**验证**：JMW_V3FULLGPU=1 下 sparse_30 对拍（G0a：原子漂移门）→ ALL_raw 399 帧 → ctest；计时预期 c7merge 0.82→~0.15ms（含下载）、单步净收益转正（4.22→~3.6ms）。

**已知坑**：pairSum 下载尺寸按实际 S 不是 512 定容；行桶 Σ 上限按 G-1 ΣR 分布（S 中位 73×行~300≈2.2 万，40 万预算充裕）；dense 33MB 只此一份（多 lane 实例注意——3 lane=100MB，可降 float 或分块）。
