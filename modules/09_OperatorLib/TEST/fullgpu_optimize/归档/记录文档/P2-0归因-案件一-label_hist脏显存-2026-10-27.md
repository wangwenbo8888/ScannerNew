# P2-0 崩溃归因档案·案件一告破（2026-10-27）

## 案件编号与症状
**案件一：SyntheticBasicMatch 顺序依赖失败族**
- 症状 A：全套测试必挂、单测必过（窗口期 5/5）；二分至最小组合
  `ChannelsAccountingAndSerialParity + SyntheticBasicMatch` 3/3 必挂
- 症状 B（同根）：断言 `trackTotal=193629（预期 1）`＋警告
  `segOverflow=1 (segCount=193629 >4096)`
- 症状 C（同根加重）：全套场景 SEH 0xC0000005
- 关联样本：ABBA 期间 speed_replay 0xC0000409（4/16 臂次，双臂均中）；
  warmup 证伪案中 flat Warmup 静默死亡（同窗活跃）——**候选同族，未证实**

## 破案链（全证据链存档）
1. 劣化窗口（61h 开机）使 bug 活跃度升高 → 二分法可复现（干净窗口潜伏）
2. 最小组合 3/3 确定性复现 → 抓到 segCount=193629=trackTotal（同一脏值）
3. 脏值来源＝`d_counts_[2]` 回读（段计数）→ 上溯 `d_label_hist_`
4. **根因**：`laser_match_scan_v3_split_front.cu` 三处位点（legacy :915 / deferred
   融合 :1178 / deferred 独立 :1261）的 hist 帧首 memset 被性能优化删除
   （注释自证"批0·C(d) Rank 自清 hist——帧首 1MB memset 已删，仅扩容兜底"），
   依赖 kernelLabelRankV3 的"自清"不变量。**该不变量在脏显存场景有洞**：
   Collect 只写触碰过的桶 → 未触碰桶携带上一使用者（或被复用显存的任意旧主）残留
   → segCount 读到垃圾。单测全过的原因＝新分配显存恰好是零页。
5. 生产相关性：fivechain 每帧跑同款延迟路径——**生产中显存永远复用（脏）**，
   本 bug 在产线是现实风险（尤其标记帧/空帧等 Collect 触碰面小的输入）

## 修复（commit b93eea2）
- 三处位点全部恢复**无条件帧首清零**（1MB memset ≈几十 µs/帧）
- 验证门全过：2 测组合 5/5（修复前 0/5 过）、全套 ×2 全绿、399 对拍 diffs=0、
  census C2 105.91（+1＝该 memset 的诚实计数代价）
- 修复后直跑稳定性：3/4 正常（修复前同窗 ~50% 异常）——**残留 1 例**说明
  家族可能还有第二名成员（0xC0000409 案未结），继续归因
