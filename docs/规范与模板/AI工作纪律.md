# AI 工作纪律（强制约束）

> 定版：2026-11-01（用户裁定）。本文档是 AI 在本工程工作的**纪律红线**，优先级高于一切效率考量。违反即事故。

## 一、职责边界（只做四件事）

```
AI 负责：① 修改代码  ② 编译  ③ 自动化测试（ctest）  ④ 提交上传（git）
人工负责：拍板决策 ＋ 真机/运行验证 ＋ 需求与优先级
```

**AI 不做**：启动 exe 跑扫描、改生产 config 默认值、删代码、未经批准 push、替人工下结论。

## 二、停等纪律（最重要）

每个关口完成后**必须停下等人工拍板**，禁止连续闯关：

```
改代码 → 编译绿 → ctest 绿 → 【停·等拍板】→ 提交推送 → 【停·汇报完毕】
```

- 测试绿 ≠ 可以提交。提交是拍板点，不是流程的自动下一步。
- 一轮只做一件事：人工报一个问题 → 修这一件 → 停。不顺手修别的、不搭车改动。
- 人工说「继续」才可以继续；沉默不等于同意。

## 三、禁区清单（未经明确指令不得触碰）

1. **git commit/push**——测试绿后停，报清单等批准
2. **默认参数**——行为影响的默认值变更（环境变量默认、门限、开关翻转）必须先报方案
3. **删除/退役**——死代码、旧机制、旧文档，判定再准也不删，只报
4. **生产 config**——`build/bin/*/config/` 下部署配置的替换与写入
5. **公共头**——改动＝契约指纹变化＝全量重编（须明示后果再动）
6. **factory_calib/**——只读保护区，不读不改不编不测
7. **结论性文档**——AGENTS.md / 开发进度.md / 工程地图.md 的定版结论须拍板
 8. **目录说明自更新**——下层「目录名-说明与交接.md」未经人工触发（「更新 XX 说明」等明示）不得更新；觉得过期/代码变了只报告提醒（规范 §2.3 反向闸门）
 9. **存量档案**——`docs/存量档案/` 人工不指定不读；需要历史时先请示（规范 §2.6）
 10. **真机操作**——不启动 exe、不跑真机扫描、不替人工「看一下效果」

## 四、编译纪律

1. 编译前查 `LeadScannerK2.exe` 是否在跑——在跑就报「请关 exe」，不硬编
2. 编译前杀孤儿 `MSBuild/cl`（VS 开着 sln 会自动抢构建抢锁）
3. 构建失败先报**原始错误**，不静默重试掩盖
4. Release 优先（用户口径：真机用 Release）；改公共头后全量重编并说明
5. 不在 build/ 里手工改产物绕问题

## 五、测试纪律

1. ctest 全量绿才算完成；红则回改，不带病过关
2. 新增诊断工具（gtest 用例）可自跑——离线分析属于我的职责
3. exe 运行验证、3D 目测、真机扫描——**全部归人工**，我最多给验证清单和判读标准
4. 不拿单次通过的日志当结论，报数字要带对比基线

## 六、汇报纪律（先事实后方案）

每轮改动汇报固定格式：

```
改了什么：文件＋行为差异
为什么：  数据/日志证据
怎么验证：人工要看的日志行/数字/现象
风险：    可能影响的旁路
```

- 诊断结论**先报实测事实**（数字/现象），方案单列等拍板——不把方案包装成既成事实
- 不确定就说不确定；推测必须标「推测」
- 修不好要如实说修不好＋卡在哪，不粉饰「部分改善」

## 七、数据纪律

1. 日志/PLY/checkpoint 分析结论附原始数字（均值/σ/样本数），不只给定性
2. 修参数前先测基线，改后报前后对比
3. 我的历次误判教训（防重蹈）：
   - dz 逐帧补偿注入噪声（把测量噪声当信号）
   - MKZ 方向搞反（+1.6 该减不该加）
   - 位姿平滑两轮无效仍先押注（散点真凶在融合门）
   - 教训共性：**先量化结构，再动手；一轮只验证一个假设**

## 八、协作约定

- 人工反馈「跑完了/没效果/好一点」→ 我立即查日志/数据核实，不空对空讨论
- 长任务（重编全量/长测试）先报预计时长
- 会话收尾：更新 开发进度.md 快照（结论性内容先拍板）
