## 0. 三项架构决策（已确认）

| # | 决策 | 含义 |
|---|---|---|
| 1 | **MCU 判连按+序号 / PC 管菜单与门控**（混合） | MCU 负责时序敏感的短按/连按2下判定 + 维护序列计数器；PC 负责菜单层级、扫描就绪门控、动作映射 |
| 2 | **隐式反馈（无专用 ACK）** | PC 不回专用确认报文；接受→翻译为已有 N10–N16 或本地执行，拒绝→默默丢弃 |
| 3 | **紧凑型 `K<ID><TYPE><SEQ>;`** | 上行报文格式：键号字母（U/L/M/R）+ 按型字母（S/D）+ 序号 |

**链路性质**：本协议为 **MCU→PC 单向上行扩展**，与协议表 N10–N16（PC→MCU 下行）正交，不冲突、不替代。

## 1. 总览与分工

### 1.1 职责切分

| 侧 | 负责 | 不负责 |
|---|---|---|
| **MCU**（下位机） | 消抖；短按/连按2下判定；维护每(键,按型)独立序列计数器；按约定格式上报 | 不知道菜单层级；不判定扫描就绪；不映射动作 |
| **PC**（上位机） | 扫描就绪门控；菜单层级状态机；上下文动作映射→翻译 N10–N16 或本地执行 | 不管消抖/连按时序 |

设计意图：MCU 固件一次稳定（时序参数不折腾、不发版）；菜单/动作逻辑全在 PC 侧，随时迭代不牵动下位机。

### 1.2 端到端报文流示例

中键短按第1次，请求开始采集：

```
用户按中键 → MCU 消抖+判=短按 → seq[M][S]++ =1 → 上行 "KMS1;"
PC 收到 → menu.layer==1 且 seq 奇 → 请求开始采集
  → 扫描就绪? 是 → 发 "N11 H1;" + 置"采集中"
                 否 → 丢弃(隐式反馈, 用户无操作反馈)
```

### 1.3 与现有协议表的关系

- 协议表 `下位机协议命令列表.xlsx` 覆盖 **N10–N16**（PC→MCU 下行命令），**无按键定义**。
- 现 MCUDriver 解析的 `K1;/K0;`（匿名、单按下/松沿）**不在协议表中**，属历史临时实现，由本协议替代。
- 本协议填补"按键上行"空白，与 N10–N16 各走各的道。

## 2. 上行报文格式规约

### 2.1 BNF 文法

```
key_report ::= "K" key_id press_type seq_no ";"
key_id     ::= "U" | "L" | "M" | "R"      ; 上/左/中/右
press_type ::= "S" | "D"                   ; S=短按1下, D=连按2下
seq_no     ::= digit { digit }             ; ≥1 的正整数
```

### 2.2 字段编码

| 字段 | 取值 | 含义 |
|---|---|---|
| 前缀 | `K` | 固定，标识按键事件（保留与历史 `K1;/K0;` 同前缀） |
| `key_id` | `U` | 上键 |
|        | `L` | 左键 |
|        | `M` | 中键 |
|        | `R` | 右键 |
| `press_type` | `S` | 短按1下（按下→松开，单次，时长 < `T_short`） |
|            | `D` | 连按2下（`T_short` 内两次合法短按） |
| `seq_no` | 1,2,3,... | 该(键,按型)组合的独立单调计数器，每事件 +1 |

### 2.3 报文示例

| 报文 | 语义 |
|---|---|
| `KMS1;` | 中键 短按 第1次（奇→请求开始采集） |
| `KMS2;` | 中键 短按 第2次（偶→请求停止采集） |
| `KMD1;` | 中键 连按 第1轮（→精细扫描） |
| `KMD2;` | 中键 连按 第2轮（→深孔扫描） |
| `KMD3;` | 中键 连按 第3轮（→普通交叉，默认） |
| `KUS1;` | 上键 短按 第1次（奇→进入菜单选项） |
| `KUS2;` | 上键 短按 第2次（偶→退出菜单选项） |
| `KUD1;` | 上键 连按 第1次（奇→视野调节） |
| `KUD2;` | 上键 连按 第2次（偶→亮度调节） |
| `KLS1;` | 左键 短按 第1次（→减值/左移，seq 仅供追溯） |
| `KRS1;` | 右键 短按 第1次（→加值/右移） |

### 2.4 PC 解析规则

替代 `MCUDriver::parseReceived` 中现有 `K1;/K0;` 分支：

- 长度 ≥ 5，`data[0]=='K'`，`data[1] ∈ {U,L,M,R}`，`data[2] ∈ {S,D}`，`data[3..]` 为数字，末尾 `;`。
- 非法/不完整 → 丢弃 + `spdlog::warn`（不阻塞接收线程）。
- 解析结果承载到 `McuEvent`（扩展 `keyId` / `pressType` / `seqNo` 字段，或在 `param1/param2` 编码——属实现侧决策）。

## 3. 预定义动作映射表（核心交付物）

> 该表为 PC 侧"按键请求 → 动作"映射规约，PC 据此执行。
> **门控**：所有动作仅在 PC 处于「扫描就绪」态（设备状态机的 **S2 待机**）时生效，否则丢弃。

### 3.1 中键（M）

| 报文 | 上下文 | 请求动作 | PC 执行 / 命中命令 |
|---|---|---|---|
| `KMS` 奇 | `menu.layer == 1` | 开始采集 | 扫描就绪 → `N11 H1;` |
| `KMS` 偶 | `menu.layer == 1` | 停止采集 | `N11 H0;` |
| `KMS` * | `menu.layer == 2` | 进入当前选项并退出菜单 | 本地：执行选中项 + `layer = 1` |
| `KMD` round = `((seq-1) % 3 + 1) == 1` | — | 切换精细扫描模式 | 本地 `mode = Fine`（影响下次 N10 参数） |
| `KMD` round == 2 | — | 切换深孔扫描模式 | 本地 `mode = DeepHole` |
| `KMD` round == 3 | — | 切换普通交叉扫描（默认） | 本地 `mode = Cross` |

**要点**：中键 short 在 layer1 / layer2 动作不同——这正是混合分工的体现（MCU 不知 layer，PC 用本地状态分叉）。

### 3.2 上键（U）

| 报文 | 请求动作 | PC 执行 |
|---|---|---|
| `KUS` 奇 | 进入菜单选项（切到第2层） | 本地：`layer = 2, cursor = ①` |
| `KUS` 偶 | 退出菜单选项（回第1层） | 本地：`layer = 1` |
| `KUD` 奇 | 进入视野调节功能 | 本地：`adjustCtx = 视野` |
| `KUD` 偶 | 进入亮度调节功能（曝光 + 补光 + 激光联动，初始默认） | 本地：`adjustCtx = 亮度` |

**菜单第2层游标 ①–④**：① 正常视野扫描；② 大视野扫描；③ 扫描完成；④ 开始后处理。

### 3.3 左键（L）/ 右键（R）

| 报文 | 上下文 | 动作 |
|---|---|---|
| `KLS` | `menu.layer == 2` | 游标左移（①←④环绕） |
| `KLS` | `adjustCtx != none` | 减值（步进由 PC 按 context 定） |
| `KRS` | `menu.layer == 2` | 游标右移（①→②→③→④→①） |
| `KRS` | `adjustCtx != none` | 加值 |

L/R **不区分奇偶**；`seq_no` 仅用于事件追溯与丢包检测，不参与动作判定。

### 3.4 未规定项（留 PC 实现自定）

- 中键 short 在「视野调节 / 亮度调节」子模式内的行为（文档未规定；建议 = 退出该调节子模式）。
- 左/右键步进的粒度（按 context：曝光 ms / 补光 0–255 / 激光 0–255 各自定）。

## 4. MCU 侧契约

### 4.1 时序参数（推荐值，固件实现，标定时可校准）

| 参数 | 推荐值 | 含义 |
|---|---|---|
| `T_debounce` | 20 ms | 机械抖动过滤窗口 |
| `T_short` | 400 ms | 短按最长按下时长 + 双击间隔窗口 |
| 短按判定 | 按下 → 松开，时长 ≤ `T_short` 且窗口内无第二次按下 | — |
| 连按判定 | `T_short` 内两次合法短按 | 第二次松开后立即判定为 `D` |

### 4.2 序列计数器

- **4 个独立计数器**：`seq[U][S]`、`seq[U][D]`、`seq[M][S]`、`seq[M][D]`。
- L/R 各 1 个追溯计数器（可选，仅用于丢包检测）。
- 上电 = 0；首次事件 = 1；单调递增；uint32 溢出回 1。
- **MCU 不做模运算回绕**——PC 自行算奇偶（`seq % 2`）/ 模（`((seq-1) % 3 + 1)`），更鲁棒于事件丢失。

### 4.3 上电/重启行为

- MCU 重启 → 所有 seq 归 1。
- PC 不依赖绝对 seq 值，仅用其奇偶/模，故 MCU 重启不会误导 PC（可能连续两次奇/偶，但不致错误状态；如需更严，PC 可定期心跳对齐）。

## 5. PC 侧状态机契约（消费侧）

### 5.1 门控

所有 `K*` 报文到达后，PC 先查设备状态机当前是否在 **S2 待机**（「扫描就绪」）；非此态 → 丢弃（隐式反馈）。

> 详见 `docs/plans/2026-08-09-设备状态机-design.md`。

### 5.2 菜单状态（PC 本地）

```
state MenuState {
    layer:     1 | 2          // 1=默认/采集层, 2=菜单选项层
    cursor:    ① | ② | ③ | ④  // 第2层游标
    adjustCtx: none | 视野 | 亮度
}
```

- **中键 short 动作分叉**：由 `layer` 决定（layer1 = 开始/停止采集；layer2 = 选中并退出）。
- **左/右键动作分叉**：
  - `layer == 2` → 左移/右移游标
  - `layer == 1 && adjustCtx != none` → 减值/加值
  - 否则 → 忽略

### 5.3 与 N10–N16 衔接

| 按键动作 | 翻译为 |
|---|---|
| 中键 short 奇（开始采集） | `N11 H1;` |
| 中键 short 偶（停止采集） | `N11 H0;` |
| 中键 D 模式切换 | 仅改 PC 本地 `mode`（影响下次 `N10` 采集参数选择） |
| 其他 | PC 本地状态变更，**不发下行命令** |

**不新增下行命令**——本协议纯粹是上行扩展。

## 6. 异常处理与向后兼容

| 场景 | 处理 |
|---|---|
| 报文格式非法（如 `KMX1;`、旧 `K1;`、`K;`） | PC 丢弃 + `spdlog::warn` |
| 未知 `key_id` / `press_type` | 丢弃 + warn |
| `seq_no` 跳跃（如 `KMS1;` → `KMS3;`） | warn（可能丢事件）；动作按当前 seq 的奇偶/模算，不阻断 |
| `seq_no` 回绕（uint32 溢出） | 接受；PC 不缓存历史 |
| MCU 重启（seq 归 1） | PC 仅用奇偶/模，安全 |
| 双方版本不一致 | 本协议为上行独立扩展；旧 MCUDriver 解析需同步升级（见下） |

### 6.1 向后兼容

- 现 `K1;/K0;`（匿名键、按下/松沿语义）**废弃**，由本协议替代。
- 现 `T25.3;`（温度）解析**不变**。
- 现 `E1;`（急停）语义已删（N15 重定义为温度读取，见 `docs/模块功能/08-设备管理.md` §2）。

### 6.2 MCUDriver 迁移（模块 08 后续实现项）

- `MCUDriver::parseReceived` 中 `K` 分支升级为新文法解析。
- `McuEvent` 扩展承载 `keyId` / `pressType` / `seqNo`（或在 `param1/param2` 编码）。

## 附录 A · 通俗解释（大白话版）

### A.1 「MCU 判连按+序号，PC 管菜单与门控」—— 活儿怎么分

把按键处理想成**两人合作**：

- **MCU（下位机）** = 干"察言观色"的体力活：你按得快不快？点一下还是连点两下？这是第几次？它只管**数数和判断手势**，然后喊一声"中键短按第3次！"——它**不知道你在不在菜单里、能不能扫**，也不关心。
- **PC（上位机）** = 干"拍板"的脑力活：现在能不能扫？在不在菜单第2层？这次按键该翻译成什么动作？它**不管你怎么按的**，只听 MCU 喊完结果再决定怎么办。

好处：MCU 固件写一次就稳（时序不折腾不改版），菜单逻辑全在 PC 上随时改随时发版，不用动下位机。

### A.2 「隐式反馈，无专用 ACK」—— PC 不回话

MCU 喊完"请求开始采集"后，**PC 不专门回一句"收到/同意"**。怎么算 PC 同意了？看 PC 有没有动作——

- 同意 → PC 直接干该干的（比如发 `N11 H1;` 启动扫描，或本地切个模式）
- 不同意（比如没在"扫描就绪"态）→ PC **默默丢弃，啥也不干**

就像你跟同事说"帮我倒杯水"：他倒了就是答应了，没倒就是没答应，不用他先回"收到"。

### A.3 「紧凑型 `K<ID><TYPE><SEQ>;`」—— 喊话的格式

MCU 喊的那句话长这样，比如 `KMS1;`：

```
K  M  S  1  ;
↑  ↑  ↑  ↑  ↑
按键 上中左 M 短按  S  第1次 1  句号 ;
   （键号字母） （按法字母） （序号）
```

- `K` = 开头标记，固定写"这是按键事件"
- `M` = 哪个键：`U/L/M/R` = 上/左/中/右（取英文首字母）
- `S` = 怎么按：`S` = 短按一下，`D` = 连按两下
- `1` = 这是第几次（奇偶/轮数，PC 靠它判断动作）

再举几个：`KMD3;` = 中键连按第3轮（切普通交叉模式）；`KUS2;` = 上键短按第2次（退出菜单）。

### A.4 「MCU→PC 单向上行，与 N10–N16 正交」—— 不打架

- **单向上行** = 这套协议**只从 MCU 往 PC 喊**（汇报按键），PC 不会反过来用这套格式回话。
- **与 N10–N16 正交** = N10–N16 是 PC **往下发**的命令（"开机、调亮度、启动扫描…"），是**另一条道**。两套各走各的，互不干扰、互不替代。

**一句话总结**：MCU 用一句小格式话把"谁、怎么按、第几次"告诉 PC，PC 自己判断要不要照做、怎么做——做完就完了，不用回话。
