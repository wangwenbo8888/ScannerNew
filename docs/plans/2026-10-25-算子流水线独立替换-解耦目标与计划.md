# 算子与流水线独立替换 · 解耦目标与实施计划（v1.0）

> 日期：2026-10-25 ｜ 状态：**目标定版，待人工确认排期**
> 人员口径（用户裁定）：**算子＋流水线管理＝一人开发；软件框架（app/02/06/08/10）＝另一人开发**
> 核心诉求：**OperatorLib 与 PipelineManager 就是两个动态库，编译好直接替换**——算子/流水线升级不影响软件框架，反之亦然。

---

## 一、目标定义

1. **二进制可替换**：替换 `OperatorLib.dll` / `PipelineManager.dll` 时，`LeadScannerK2.exe` 及其它模块 **无需重编**，拷贝即生效
2. **职责单一**：算子库只含算法（calib:: 三元组算子）；流水线库只含调度/编排；业务归框架
3. **契约先行**：两个库对外只暴露**稳定契约层**（工厂＋纯虚接口＋POD 数据结构）；实现细节（具体类、STL/OpenCV/Eigen 类型）不出 DLL 边界
4. **替换即验证**：替换后有现成回归闸门（speed_replay golden 对拍 ＋ 全量 ctest）

### 2.2 剩余耦合点（按伤害排序）
| # | 耦合点 | 位置 | 后果 |
|---|---|---|---|
| C1 | **具体类跨 DLL 边界**：app/02 直接使用 07 具体类（`ScanPipeline`/`ScanChains`/`FrameObsAccumulator`），07 直接 new 算子具体类（ScanChains.cpp 直接 include 46 个算子头） | app/AppContext.cpp、02/ScanWorkflow.cpp、07/ScanChains.cpp | 任一头文件加字段/虚函数 → 全链重编；DLL 无法单独替换 |

## 三、目标架构（三层）

```
┌─────────────────────────────────────────────────────┐
│  软件框架（框架开发者的领地）                          │
│  LeadScannerK2.exe ＋ 06/08/10 DLL                   │
│  只依赖：op_registry.h ＋ pipeline_registry.h        │
│         （纯虚接口＋POD 契约头，随库发布）            │
└──────────────┬──────────────────────┬───────────────┘
               │ 工厂导出（C 符号）    │
┌──────────────▼──────────┐ ┌─────────▼──────────────┐
│ OperatorLib.dll          │ │ PipelineManager.dll    │
│ （算子开发者领地）        │ │ （流水线开发者领地）     │
│  · op_registry：         │ │  · pipeline_registry： │
│    create(id)->IOperator │ │    create()->IPipeline │
│  · 算子实现（内部符号）   │ │  · 五链执行器/调度（内部）│
│  · 版本协商 op_abi_ver() │ │  · 经 op_registry 用算子│
└─────────────────────────┘ └────────────────────────┘
```

关键规则：
1. **契约头独立目录**：`modules/OperatorLib/api/`、`modules/PipelineManager/api/`——只放纯虚接口＋POD＋工厂 C 符号声明。这是唯一允许跨界 include 的目录，随 DLL 一起"发布"
2. **跨界只传三类东西**：①纯虚接口指针 ②固定布局 POD（对齐 CloudViewHandle 现有形态）③基本类型。STL/OpenCV 对象一律不出边界（边界处转 POD 数组或由接收方传入缓冲）
3. **版本协商**：每个 DLL 导出 `extern "C" uint32_t jmw_abi_version()`；框架加载时校验，不匹配拒绝加载并明确报错
4. **数据所有权**：谁分配谁释放（工厂成对 create/destroy；缓冲由调用方提供）

## 四、实施计划（结合现状，最小扰动路线）

### 阶段 D1：算子库契约层（先做——它是流水线契约的前置）
- 新建 `modules/OperatorLib/api/`：`op_registry.h`（`IOperator` 纯虚＝Execute(void* params, void* result)/Warmup/Destroy 三口＋算子 id 枚举/C 字符串）＋ `jmw_op_export.h`（C 工厂）
- OperatorLib 内新增 `op_registry.cpp`：id→实例的分派表（算子开发者后续新增算子只在此登记）
- Params/Result 跨界形态：**保留现有 C++ 结构体但冻结布局**（Phase 1 后已定版；后续加字段走「新 id 新结构」而非改旧结构）
- 验收：PipelineManager 改经 registry 取算子后，OperatorLib.dll 换文件（同契约）app/07 不重编，golden 对拍绿

### 阶段 D2：流水线库契约层
- 新建 `modules/PipelineManager/api/`：`pipeline_registry.h`（`IScanPipeline`/`IPosturePipeline`/`IGlobalOptim` 纯虚——方法对齐现有 IWorkflow 调用面但只传 POD/接口指针）＋ C 工厂
- 02 ScanWorkflow（编在 exe）改为只调 api 接口；`ScanPipeline`/`ScanChains`/`FrameObsAccumulator` 移入 DLL 内部（头不出库）
- 观测账本（FrameObs 快照）经 POD 化 `ObsSnapshotView` 出库（对齐 CloudViewHandle 手法）
- 验收：PipelineManager.dll 单独替换，app 不重编，扫描全流程真机可跑

### 阶段 D3：构建解耦与替换工作流（工具化）
- 两库独立版本号（`OP_VERSION`/`PM_VERSION` 资源＋导出版本串）；替换工具脚本：拷 DLL＋比对 abi_version＋自动跑 speed_replay 对拍＋ctest——绿灯才允许交付
- CI/本地「契约头快照」校验：api/ 目录 hash 与 DLL 内嵌契约 hash 一致
- 验收：模拟"算子开发者单独交付新 OperatorLib.dll"演练一次全绿

### 与既有计划的关系
- **不与 Phase 2（五链执行器）冲突**：D1 先行（纯加法）；D2 与 Phase 2 合并实施——五链执行器本就藏在 PipelineManager 内部，契约层恰好按目标形态设计，避免二次返工
- 排期建议：D1＝2 天；D2＋Phase 2＝5-7 天；D3＝2 天

## 五、风险与对策
| 风险 | 对策 |
|---|---|
| POD 化改造量失控（历史接口大量 cv::Mat） | 分级：**配置/状态类先 POD 化**（高频变更面）；大对象（点云/图像）走"句柄＋destroy 回调"（CloudViewHandle 先例） |
| 双人并行开发契约漂移 | api/ 目录双人评审＋版本协商硬校验 |
| 性能损耗（工厂/虚调用/拷贝） | 一次性 create 常驻（非每帧工厂）；点云跨界本就走共享指针句柄，无逐帧拷贝 |
| C2 短期无法根除（OpenCV 对象暂留） | 过渡期锁死「同 VS2022/同 /MD/同 OpenCV 4.13」于 abi_version 校验中一并检查 |
