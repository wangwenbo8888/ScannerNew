## 0. 背景与目标

### 0.1 问题

原三层结构 `framework/ + modules/ + app/` 中，`framework/` 沦为"无主共享杂物间"——大量代码不属于任何单一模块，归属不清，且夹杂死代码。`framework优化.md` 提议删 framework/、内容分发给各模块，但该提议有两处硬伤：

1. **公共类型 → `app/types.h`**：层级倒置（底层砖块放屋顶），需开"模块依赖 app"的后门。
2. **EventBus → `modules/07_session`**：逼设备层（08）反向依赖编排层（07），且与权威治理 `06-文件管理 §2`（数据容器归 06）在落点上直接冲突。

### 0.2 本方案目标

- 消灭 framework/ 杂物间（认同 `framework优化.md` 的目标）。
- 修两处硬伤：为"无主横切设施"留一个**极薄底座 `core/`**。
- 与 `06-文件管理 §2` 权威治理对齐：数据容器统一归 06。
- 给四个状态机（顶层/外设链路/按键/帧生命周期）明确落点。
- 单向依赖、无环、无例外后门。

## 1. 分层总览

**结构：一个底座 + 一个顶 + 中间按依赖排序的模块。** 自底向上 6 层，依赖只能往下。

```
┌──────────────────────────────────────────────────────────────────┐
│ ⑥ app/              装配根：AppContext(所有权/DI) + MainWindow + 工作流装配 │
├──────────────────────────────────────────────────────────────────┤
│ ⑤ 业务层   01标定 02扫描 03渲染 04后处理 05编辑 09算子 10可观测 11部署      │
├──────────────────────────────────────────────────────────────────┤
│ ④ 编排层   07_session：设备顶层 FSM(S1–S7) + SessionService + 工作流编排   │
├──────────────────────────────────────────────────────────────────┤
│ ③ 设备层   08_devicemgmt：HAL + 驱动 + 监控 + 外设链路FSM + 按键FSM        │
├──────────────────────────────────────────────────────────────────┤
│ ② 数据层   06_fileio：运行时容器 + Sink + 文件IO + L4产物仓库             │
├──────────────────────────────────────────────────────────────────┤
│ ① core/    共享内核：types.h + EventBus + 日志/时间（仅此三样）           │
└──────────────────────────────────────────────────────────────────┘
   依赖只能往下；core 谁都可踩，不踩任何人
```

## 4. 关键决策与铁规

### 4.1 三项关键决策（为什么这么分）

1. **`core/` 独立成最底层**——修 `framework优化.md` 的两处硬伤。类型和事件总线是"无主横切"，**不能塞给任何业务模块**（塞给 app 是层级倒置；塞给 07 是逼 08 反向依赖）。放最底，谁都可踩，问题根除。
2. **数据容器全归 06**（遵 `06-文件管理 §2` 权威治理）——不拆散到 08。数据设施集中一处，避免散落。08 的硬件监控把状态**写进** 06 的 DeviceStateCache（依赖 06），不自己持有。
3. **编排(07)在设备(08)之上**——语义正确（先有设备才能编排）。08→07 的反向依赖**消失**：08 用 core 的 EventBus 发事件，07 订阅，互不直接依赖；07 命令设备时才单向依赖 08。

### 4.2 铁规（防止 core/ 腐化成 framework/ 2.0）

> **`core/` 只准放 types / EventBus / 日志时间三样，禁止任何业务代码。** 新增项需审批。
>
> 这是 framework/ 当年缺失的纪律。没有这条铁规，core/ 迟早又被塞成杂物间，本方案失败。

### 4.3 与 `framework优化.md` 的差异

| 硬伤 | `framework优化.md` | 本方案 |
|---|---|---|
| 公共砖块去哪 | types→app（层级倒置）、EventBus→07（逼 08 反求 07） | **单设 `core/` 作底层** |
| 数据容器落点 | 拆散（帧/状态→08），与权威 06 冲突 | **全归 06**（遵 `06-文件管理 §2`） |

> **修订注（二次审查）**：原表第三行"CalibStore 双标"经代码核实**撤销**——CalibStore 非孤儿（`AppContext.cpp:35` 创建+`:66` 注入、`CalibrationWorkflow.cpp:9` 引用、由 `framework/workflow/CMakeLists.txt` 编译）。`framework优化.md` 迁 CalibStore 入 01 是**对的**；我上一轮将其批为"双标"是误判。本方案改为：迁入 01 + 补写入 TODO + 采纳 `calib_result_types.h` 契约（见 §2.5）。

## 5. 状态机落点

本工程共 **4 个状态机**（详见会话内"4 状态机分层方案"分析），落点如下：

| 状态机 | 层 | 落点 | 触发源 |
|---|---|---|---|
| 设备顶层 FSM（S1–S7） | ④ 编排 | `modules/07_session` | 用户动作/完成事件/故障 |
| 外设链路 FSM（MCU + Camera 双实例） | ③ 设备 | `modules/08_devicemgmt` | 定时器/串口 I/O/USB 事件 |
| 按键交互 FSM | ③ 设备 | `modules/08_devicemgmt` | MCU 按键事件 `K<ID><S/D/H>;` |
| 帧生命周期 FSM（流水线阶段） | ⑤ 业务（调度） | `modules/09_operatorlib` E 核 | 帧数据流（高频） |

**协作关系**：外设链路 FSM 上交 `FaultOccurred` → 顶层 FSM 进 S7；按键 FSM 上交 `KeyPressed`/动作请求 → 顶层 FSM；按键 FSM 仅在顶层 FSM = S2 待机时活跃（被门控）。

## 6. 依赖规则

```
core ← 06 ← 08 ← 07 ← 业务 ← app
```

- **单向、无环**。任何层不得依赖上层。
- `core/` 不依赖任何人。
- `app/` 不被任何人依赖（装配根）。
- `framework/` 整树退役（迁移完成后删除）。
- 模块间尽量不直接依赖；必须时走 EventBus 事件解耦，或经 core 共享契约。

## 8. 迁移顺序建议（落地路径）

> 原则：先底座、再数据、后设备/编排、最后删 framework/。每步可独立编译验收。

1. **建 `core/`**：从 `framework/common`+`framework/infra` 抽 types.h（拆分）+ EventBus，建 `core/` 库；全局 include 改向。
2. **迁数据层**：`framework/data` 容器 + Sink → `modules/06`；DeviceState 枚举 → 06；`framework/service/ParameterManager` → 06；**`framework/workflow` 的 IWorkflow/Pipeline/Stage → 06**（工作流框架下沉：Stage 被模块 stages 继承，必须低于业务层，六审）。**例外**：`CalibStore` → `modules/01`（非 06，已核实为活代码，见 §2.5）。
3. **迁设备层**：`framework/hal` → `modules/08`；改 08 的 include 指向 core + 06。
4. **迁编排层**：`framework/service`（StateMachine/SessionService/IState）→ `modules/07`；EventType/Event → 07。
