## 0. 起点现状（三轮代码审核结论）

> 不是"状态机空转"，而是"半接线 + 死代码"。

### 现有实现
- `ScannerState` 枚举 9 态：Init/DeviceReady/Calibrating/Calibrated/Scanning/Paused/PostProcessing/Error/EmergencyStop（`framework/service/IState.h`）
- `StateMachine::transition(EventType)` 命令式 + `isValidTransition` 表 + 发 `StateChanged`（`framework/service/StateMachine.cpp`）
- `EventType` 枚举（`framework/common/types.h:120`）
- `FaultHandler`：订阅 `FaultOccurred`（`FaultHandler.cpp:13`）→ 自动 `transition`→Error；`reportFault/clearFault` 已有但**无外部调用者**

### 接线现状（运行时）
| 转换/事件 | 驱动 | 状态 |
|---|---|---|
| DeviceConnected (Init→DeviceReady) | `ScannerWindow.cpp:273` 相机开 | ✅ 通 |
| DeviceDisconnected (→Init) | `ScannerWindow.cpp:287`相机关 | ✅ 通 |
| FaultOccurred (→Error) | FaultHandler 订阅；**无探测器 publish** | ⚠️ 半接 |
| ScanStarted/Stopped | `ScanWorkflow.cpp:296/324` 有 publish，但 `start()` 在 `ScannerWindow.cpp:326` **被注释** → 死代码；状态机也非订阅式 | ❌ 死/未接 |
| ScanPaused / SessionStarted / DeviceError | 无发布、无调用 | ❌ 未用 |

### 关键事实
- `ScannerWindow` 对框架 `scanWorkflow()`：`setProgressCallback`(125) ✅、`stop`(346) ✅、`start`(326) ❌注释 → 框架扫描工作流**装配却闲置**。
- `MainWindow::onScanClicked` 走 `calibration::ScanWorkflow`（标定模块），不用框架工作流、不驱动状态机。
- `SessionService::loadCheckpoint` 不解析（TODO）→ 续作依赖缺失。

---

## 1. 目标
将 `ScannerState` + `StateMachine` 演进为 §5 的 7 状态模型（S1 Init / S2 Standby / S3 Calib / S4 ScanMarker / S5 ScanMarkerLaser / S6 Post / S7 FaultSelfCheck），含 S4/S5 的 就绪/采集 子态、S7 安全停机与续作恢复，并接通"探测→故障→S7"与"UI→状态机→框架工作流"两条断链。

---

## 2. 架构抉择（推荐，待你拍板）

| 抉择 | 选项 | 推荐 | 理由 |
|---|---|---|---|
| **A 触发架构** | ①状态机订阅 EventBus 自动反应 / ②命令式 transition | **①事件驱动** | FaultHandler 已用订阅模式；硬件按键/通讯/故障天然异步；统一为单一事实源，消除"谁该调 transition"的混乱 |
| **B 子态建模** | ①扩 ScannerState 枚举 / ②顶层枚举 + 独立 `ScanSubState` 字段 | **②独立子态字段** | 顶层 7 态互斥不变，就绪/采集 是扫描内部细节，不污染顶层转换表 |
| **C S7 动作位置** | ①状态机持 `prev_` + entry action 执行安全停机 / ②独立动作表或 StateChanged 订阅者 | **①状态机内** | 恢复回 `prev_` 需状态机记前态；entry action 集中可见 |

> 决策门：A/B/C 一经确认，每阶段即可拆为 TDD 逐任务（写失败测试→实现→通过→提交）。

## 3. 实施阶段（按依赖排序）

### 阶段 0 · 枚举与转换表对齐（地基）
**文件**：`framework/service/IState.h`、`StateMachine.cpp`、`common/types.h`
- `ScannerState` 改为 7 态：`Init / Standby / Calibrating / ScanMarker / ScanMarkerLaser / PostProcessing / FaultSelfCheck`（删 `DeviceReady`(改名 Standby)/`Calibrated`(改出口事件)/`Paused`(并入子态)/`Scanning`(拆 4&5)/`Error`(改名 FaultSelfCheck)/`EmergencyStop`(弃用)）
- `EventType` 补：`SelfCheckPassed / CalibStarted / CalibDone / ScanModeMarker / ScanModeMarkerLaser / KeyPressed / Recovered`（按需）
- 重写 `isValidTransition` 为 §5.3 转换表（S6 免疫：不收 FaultOccurred；S7→退出前状态）
- 重写 `canOperate`
- **测试**：纯状态转换表，最适合 TDD——每条合法/非法转换一个测试。

### 阶段 1 · 状态机改为 EventBus 订阅式（抉择 A①）
**文件**：`StateMachine.cpp`、`AppContext.cpp`
- `StateMachine::start(eventBus)`：订阅 DeviceConnected/Disconnected、FaultOccurred/Cleared、SelfCheckPassed、KeyPressed、ScanMode* 等 → 内部 `transition()`
- 保留 `transition()` 为内部/private（外部只发事件）
- `AppContext`：`stateMachine_->start(eventBus_)`
- **测试**：发事件 → 断言状态变化；旧命令式调用点（ScannerWindow:273/287）改发事件。

### 阶段 2 · S7 entry action + prev_ 记忆（抉择 C①）
**文件**：`StateMachine.cpp`；依赖 `modules/08_devicemgmt/{CameraControl,MCUDriver}`
- 进 S7：记 `prev_ = 当前态`；执行安全停机（`camera->stopAsyncCapture()` + `mcu->setLedOn(false)` + `mcu->setLaserOn(false)`）
- S7→Recovered：回 `prev_`（不恒回 Standby）
- **测试**：制造 FaultOccurred → 断言进 S7 + 硬件停止命令发出 + prev_ 记录；Recovered → 回 prev_。

### 阶段 3 · 故障探测链（接通"半接"）
**文件**：`modules/08_devicemgmt/HardwareMonitor.cpp`、`MCUDriver.cpp`、`CameraControl.cpp`
- HardwareMonitor：温度阈值 → `eventBus->publish(FaultOccurred)`（当前只发 TemperatureUpdate）
- MCUDriver：串口超时/断连 → publish FaultOccurred
- CameraControl：USB 断连检测 → publish FaultOccurred
- GPU 故障：算子 `Result` 失败 →（仅 S4/S5 路径）上报；S6 内部走 Result 不进 S7
- **测试**：模拟温度越限/串口超时 → 断言 FaultOccurred 发出 → 状态机进 S7。

### 阶段 4 · S4/S5 就绪/采集子态（抉择 B②）
**文件**：新增 `ScanSubState`（就绪/采集）；`SessionService` 或 `ScanWorkflow` 持有；`MCUDriver` KeyEvent 路由
- 扫描入口（S2→S4/S5）落"就绪"；MCU `KeyEvent`(K1/K0) → 子态 toggle（就绪↔采集）
- 上位机图标 → 发"回 Standby"事件（无论就绪/采集）
- **测试**：进 S4→就绪；发 KeyPressed→采集；再发→就绪；发"回 Standby"→S2。

### 阶段 5 · 扫描链接通（消除双轨）
**文件**：`modules/02_scanning/ScannerWindow.cpp`、`app/MainWindow.cpp`
- 取消 `ScannerWindow.cpp:326` 注释，接通框架 `scanWorkflow()->start()`
- `MainWindow::onScanClicked` 改为：发"启动扫描"事件 → 状态机转 S4/S5 → 框架 ScanWorkflow 启动（**不再直接 new `calibration::ScanWorkflow`**）
- 标定同理：`onCalibDeviceClicked` 走状态机 + 框架 `calibWorkflow`
- **风险高**：影响 UI 行为，需回归测试。

### 阶段 6 · S7 续作（依赖检查点）
**文件**：`framework/service/SessionService.cpp`（`loadCheckpoint` 解析）、`StateMachine.cpp`
- 实现 `loadCheckpoint` JSON 解析（当前 TODO）
- S7 恢复回 S3/S4/S5 时，续作同一会话（接续断点，中间留缺口）
- 周期自动存盘（每 N 帧 saveCheckpoint）
- **测试**：存 checkpoint → 进 S7 → 恢复 → 断言会话续作。

### 阶段 7（可选/后置）· S1 自检实质化
**文件**：`modules/08_devicemgmt`（上电自检 + 许可证，均 TODO）
- 启动跑通讯/加密狗/授权自检 → 全过发 `SelfCheckPassed` → S2
- 非通讯失败（加密狗/授权）→ 留 S1 阻塞
- 依赖模块8 自检与许可证实现（独立工作项）。

## 4. 依赖与风险
- **硬依赖**：`SessionService::loadCheckpoint` 解析（阶段6）、模块8 上电自检+许可证（阶段7）。
- **主要风险**：
  - 阶段 5 双轨改造影响 UI 行为，回归面大。
  - 阶段 1 状态机改订阅式后，事件顺序/线程安全（EventBus 跨线程发布）需明确。
  - 枚举改名（阶段 0）会破坏现有 `isValidTransition`/`canOperate` 与测试，需全量更新。
- **建议顺序**：0→1→2→3→4 是"状态机本体"主轴（可独立验收）；5 是"接通 UI"的高风险高价值步；6/7 依赖外部工作项。

---

## 5. 验收标准（每阶段）
- 阶段 0：转换表测试全绿，覆盖 §5.3 全部合法/非法跳转 + S6 免疫 + S7 回 prev_。
- 阶段 1：事件驱动下，DeviceConnected/FaultOccurred/KeyPressed 等均能正确转态；无残留命令式调用。
- 阶段 2：进 S7 时相机/补光灯/激光停止命令实际下发（mock 验证）。
- 阶段 3：温度/通讯故障能触发 S7（端到端）。
- 阶段 4：硬件按键 toggle 就绪/采集，图标回 Standby。
- 阶段 5：UI 扫描/标定走状态机 + 框架工作流，`calibration::*Workflow` 旁路移除。
- 阶段 6：S7 恢复后续作同一会话。
