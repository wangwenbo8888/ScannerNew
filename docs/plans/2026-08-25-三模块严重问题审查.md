# 代码审查发现 — 06/07/08 三模块严重问题（2026-08-25）

> 审查范围：modules/06_fileio（数据管理）、modules/07_pipelinemgmt（流水线管理）、modules/08_devicemgmt（设备管理）。
> 只列严重问题；结构性分层、线程模型、生命周期契约经抽样核实一致，不在此列。
> 每条附代码/文档证据位置。

## 一、06 数据管理

### 1. 无上限内存增长（会话时长硬顶）
- **现状**：`PointCloudBuffer`（06 全局点云仓库）与 `FrameObsAccumulator.obsList_`（07 逐帧观测）只增不清，长会话内存无界增长。
- **量化**：激光融合累积 8.6-86 MB/s 流入；32GB 本机估算仅支撑约 10 分钟会话，之后 OOM/换页拖死全进程。
- **证据**：FrameObsAccumulator.h:10 自认「obsList_ 无上限增长、万帧级实测后评估」；PointCloudBuffer 同款无界。
- **修复方向**：预算硬顶＋分窗落盘；超限降级已有先例（激光缓存 2048MB 预算制）可复用。

### 2. 姿态环槽位硬编码与文档冲突
- **现状**：`CalibSessionData.h:32` 固定 `kSlots = 8`；姿态调度方案 §14 定的是 `N_SLOTS = 4*X`（X=lane 数）。
- **后果**：P 链 10-20ms/周期下 8 槽反压环频繁顶满 → 阻塞 08 采集线程，姿态吞吐受限。
- **修复方向**：槽位随 lanes 推导；实测反压吞吐后定系数。

## 二、07 流水线管理

### 3. 反压死锁级联（全工程最尖锐）
- **链路**：A 姿态 lanes 卡死（不退出）→ 无人调 `done()` → CycleUnit Backpressure 环（8 槽）写满 → 08 相机回调线程在 `wrCv_.wait` 永久阻塞 → 采集整链停摆。
- **加重因素**：收口 watcher 只等 `completionRequested_ || watcherStop_`（PosturePipeline.cpp:380），不看 `lanesExited()`；`syncState` 是惰性发现——上游不来查就无人解锁、无 Fault 上报。
- **修复方向**：watcher 加 `wait_for` 周期分支查 lanesExited → 主动收口＋通知 08 停采；或环 write 加超时退路。

### 4. 全链无 hang 看门狗（猝死有检测、卡死没有）
- **现状**：只检测异常退出（1604/1701 异常即停＋惰性收敛）；三个真 hang 场景全部漏检：
  - lane `fut.wait()` 无超时（SchedulerRuntime.h:16 自认「卡死属 Broker 层故障，本层不设看门狗」）；
  - 算子死循环/极慢不触发 catch（帧边界才查 stop）；
  - syncState 惰性＝编排层不轮询则永远无人发现。
- **串行接力模型的放大**：A→B、C→D→E 前棒 hang 则后棒永不启动，整条会话链静默断链。
- **现成半成品**：SelfCheckCollector 心跳注册制已建（registerHeartbeat/beat/staleHeartbeats）但 07 无人注册——接上即得超时清单。

### 5. D→E 数据通路断裂（修正激光云无出口）
- **现状**：D 全局优化后激光云只有显存裸指针 `laserCtx`（LaserCloudFuseDeviceContext）；`LaserCloudFuseCuda` 无任何 Download/host 导出口（grep 全库仅计数镜像）；`cloudRepo_->write(tag)` 只传标签字符串（GlobalOptimObject.cpp:364）；渲染推送 `deviceLaser=nullptr` 注明「T17 细化」。
- **后果**：E 后处理（三角化/网格化，纯 host MeshData）与 STL 导出拿不到修正后激光数据——批处理模型正确（GBA 联立求解必须算完一起导），缺的是一次性下载出口＋仓库交接。
- **修复方向**：算子补 `DownloadFusedPoints`；或走 06 点云仓库中转（兑现 cloudRepo 原始设计意图）。

### 6. GBA 闭环检测依赖列表序（乱序漏闭环）
- **现状**：闭环判定按下标 `k - i <= loopFrameGap`（global_ba_cpu.cpp:157-158），假设 frames 列表序≈时间序；而 obs 列表序＝完成序，多 lane 并行下可乱序（窗口 ≤ 在飞帧数）。
- **后果**：真远隔闭环帧被排相邻 → 被 skip 漏检；当前乱序窗口（≤8-16）< loopFrameGap=30 风险低，扩 lane 后放大。
- **修复方向**：GBA 装配输入按 frameId 排序（GlobalOptimObject 装帧循环前一次 sort，laserCacheSlot 并行数组同步排）——一行级成本。

### 7. 并行扩容三处硬顶（与「多实例并行提效」目标相悖）
- `kScanGpuSlots = 2`：X lane 同时只有 2 帧做 GPU 段，其余堵 acquire 超时丢帧；
- `kLaserPoolBlocks = 8`：在飞激光显存块上限与 lanes 脱钩，满负荷时静默丢激光（50ms 超时降级）；
- FuseConsumer 单线程汇流：全 lane 结果串行消费（CPU 体素融合＋同步 D2H download），队列满整帧丢。
- **修复方向**：三参数进 ScanConfig 统一推导；融合消费多实例化或 GPU 化 marker 融合。

### 8. B/D 落盘窄接口零实现
- **现状**：`ICalibRepoWriter/ICloudRepoWriter` 全工程无实现者（grep 仅 07 自身定义）；01 现走 06 直写绕开；D 的 write(tag) 是占位。
- **后果**：文档流程图「B→06 落盘、D→点云入库」画的是完整管道，实际是空管道。

## 三、08 设备管理

### 9. 帧率协议矛盾（采集上限可能不达标）
- **现状**：IMCU.h:18 N10 协议注释 `H20-120`（freqHz 上限 120Hz）vs 设计目标 180fps（标定流水线.md:590）/200fps（扫描调度 C2）。
- **后果**：按协议表连目标帧率都发不出去；无任何一方标注此分歧。
- **修复方向**：协议方裁决 H 字段单位/上限；若真受限则帧率目标需重估。

### 10. 系统监控缺口（GPU 利用率＋处理帧率无源）
- **GPU 占用率**：HealthMetrics 无字段（base/types.h）；SelfCheckCollector NVML 只声明 Init/GetHandle/GetTemperature/GetMemoryInfo 四函数，未声明 `nvmlDeviceGetUtilizationRates`（SelfCheckCollector.cpp:43-46）——SM 利用率从未采集。
- **处理帧率/丢帧率**：`setProcessCounter/setDropCounter` 注入口无生产者；07 `SchedulerRuntime::stats()` 四计数已就绪但无人接桥（10-可观测文档 L87 自认）。
- **修复方向**：types.h 加字段＋NVML 补声明约 10 行；app 装配层把 runtime.stats() 接到注入函数。

## 四、横切风险（跨模块）

### 11. EventBus 无护栏＋持锁回调
- **现状**：`publish` 持锁遍历订阅者直接调用且无 try/catch（EventBus.cpp:6-13）。
- **后果**：任一订阅者抛异常 → 传染发布线程（可能是 08 逻辑线程或某 lane）→ 流水线停；UI 侧一个订阅 bug 能杀采集/命令链。回调内再 publish/subscribe = 自锁全总线。
- **修复方向**：逐订阅者 try/catch＋先拷订阅表再回调（去锁）。

### 12. CUDA 致命错进程级中毒（无隔离）
- **现状**：任何算子触发 fatal CUDA error（非法访存等）→ 单一 context 中毒不可恢复 → C 激光链、D 重放、GpuSlotService 全报废；软件 try/catch 挡不住异步 sticky error。
- **串行模型下的表现**：A/C 的错以 Degraded 形式「遗传」给 D（激光修正静默丢失），错误不中断链而是流向产物。
- **修复方向**：致命错误即进程重启策略（配合 10-CrashHandler）；D 的 Degraded 分支加 context 健康检查再定重放策略。
