# 标定姿态判断并行流水线调度设计文档（精简版）

> **基于 Intel CPU（X 个 P 核 + Y 个 E 核）+ NVIDIA GPU 的帧级流水线并行调度方案**
>
> 仅标定阶段 2（姿态判断）采用流水线。阶段 0/1 独立运行，阶段 3/4 为批量计算。**姿态优先**——不可丢帧以免错过目标姿态。

---

## 1. 目标与约束

### 1.1 设计目标

在固定硬件资源下，对标记点帧流水线化处理（掩膜提取→标记点链→融合→姿态判断），最大化吞吐量以**不漏检 25 个目标姿态**。姿态命中时保存整个采集周期图像（标记点帧 + 全部激光管帧）。

### 1.2 硬件约束

| 编号 | 约束 |
|------|------|
| C1 | 硬件为 Intel CPU（X 个 P 核 + Y 个 E 核）+ NVIDIA GPU |
| C2 | 1 个 P 核锁定给 Windows 系统 + 采集线程；采集循环单元（标记点帧 + N 个激光管帧 + 温度）打包写入环形缓冲区 |
| C3 | X-1 个 P 核 + X 个 E 核锁定给流水线；每流水线 = 1 P 核 + 1 E 核；E 核负责调度与融合+姿态判断 |
| C4 | 流水线空闲时从环形缓冲区抓取帧（**保守策略：不跳帧**，见 §8） |
| C5 | 自动分配并行 X 个流水线；流水线数 = 分配给流水线的 P 核数 + 1（防 P 核空闲） |
| C6 | GPU 分配 1 个槽即可（姿态链 GPU 工作量轻：仅 mask_extract + ccl）；预留显示/系统 SM |
| C7 | 姿态优先（不丢帧） |

### 1.3 算法约束

| 编号 | 约束 | 影响 |
|------|------|------|
| A1 | `optical_flow_fuse`（2-12 默认）依赖 `PrevFrameState`（上一帧标记点） | 融合需前序信息 |
| A2 | `pose_estimate`（2-13）将当前姿态与 25 个预设 4×4 矩阵逐一比对 | 姿态匹配为只读共享数据 |
| A3 | 姿态命中时需保存**整个采集周期**（标记点 + 全部激光管帧） | 环形缓冲单元须含激光帧 |
| A4 | 仅标记点链走流水线（2-1~2-13）；2-14 display 异步渲染不阻塞 | 单分支流水线，无帧内 CPU/GPU 并行 |
| A5 | GPU 仅做 2-1 mask_extract + 2-2 ccl（轻量）；CPU 标记点链 2-3~2-11 为瓶颈 | P 核是主要瓶颈 |

### 1.4 与扫描流水线的核心差异

| 维度 | 扫描流水线 | 标定姿态流水线 |
|------|-----------|--------------|
| 分支数 | 双分支（标记点 CPU + 激光 CUDA） | **单分支**（仅标记点链） |
| GPU 工作量 | 重（预处理 + 激光 04~08） | **轻**（仅 mask + ccl） |
| 瓶颈 | GPU | **P 核** |
| 终止条件 | 无限运行 | **25 姿态集齐即停** |
| 帧丢弃 | 跳最新帧 | **不丢弃**（防漏检姿态） |
| 终端算子 | 融合-02（点云输出） | **pose_estimate**（姿态判定 + 帧保存） |

## 3. 硬件资源分配

### 3.1 资源数学

| 资源 | 总数 | 分配 | 说明 |
|------|------|------|------|
| **P 核** | X | 1 → 系统/采集；**X-1 → 流水线 P 核池** | 动态租用 |
| **E 核** | Y (≥X) | **X → 流水线**（每流水线 1 个独占）；Y-X → 系统 | 静态绑定 |
| **GPU SM** | N_sm | `reservedSM` → 显示/系统；**全部剩余 → 1 槽** | 单 stream 即可 |
| **流水线数** | — | **X = (X-1) + 1** | 活跃 X-1 + 待命 1 |

### 3.2 GPU 单槽设计

姿态链 GPU 工作量仅 mask_extract + ccl（~1-2ms），远轻于扫描的双分支 GPU 工作。**1 槽足够**，无需 MPS 分配。GPU 不是瓶颈，P 核才是。

### 3.3 关键不变量

- **E 核 ↔ 流水线**：1:1 静态绑定，全生命周期不交换
- **P 核 ↔ 流水线**：X 流水线竞争 X-1 P 核，由 P-core Broker 调度
- **GPU 槽**：X 流水线竞争 1 槽，先到先得（但占用时间极短）
- **流水线 X-1**：始终作为待命位，预取 + 预处理提前完成，等 P 核释放即接管

## 4. 单帧生命周期与阶段分解

### 4.1 阶段状态机（E 核编排）

```
帧 N 生命周期（标记点帧 + 对应采集周期的激光管帧）:

状态                运行位置        算子                        等待条件
─────────────────────────────────────────────────────────────────────────
① PREFETCH          E核             (抓帧: 采集周期单元)        环形缓冲有新周期
② WAIT_GPU          —               (排队)                      GPU 槽空
② RUN_GPU           GPU 槽          2-1 mask_extract            —
                                   2-2 ccl
③ WAIT_PCORE        —               (排队)                      P核空
③ RUN_PCORE         P核(动态)       2-3 image_split             —
                                   2-4 zernike_edge
                                   2-5 image_merge
                                   2-6 undistort_cpu
                                   2-7 ellipse_fit ★
                                   2-8 marker_match
                                   2-9 epipolar_intersect
                                   2-10 edge_match
                                   2-11 point_reconstruct
④ RUN_FUSE          E核             2-12 单帧融合               —
                                   (光流优先, 失败降级特征配准)
                                   (读最新 PrevFrameState 快照)
⑤ RUN_POSE          E核             2-13 pose_estimate          —
                                   姿态匹配 25 目标:
                                   ├── 未命中 → 继续
                                   └── 命中 → 原子CAS标记, 保存周期帧
⑥ DONE              —               (释放资源, 回到 ①)
                                   (25姿态全齐? → 信号完成)
```

> **2-14 display**（如实现）为独立 CUDA 异步渲染线程，消费 2-13 输出的姿态 (R,T)，不阻塞流水线。

### 4.2 阶段并行性

| 阶段 | 资源 | 帧内并行 | 跨帧并行 |
|------|------|----------|----------|
| ② GPU 预处理 | GPU 槽 | — | 受 1 槽限制（但占用极短） |
| ③ 标记点链 | P 核 | — | 受 X-1 P 核限制（**主瓶颈**） |
| ④ 单帧融合 | E 核 | — | **E 核全并行**（读最新快照） |
| ⑤ 姿态判断 | E 核 | — | **全并行**（只读 25 目标表） |

> 与扫描不同：标定姿态链**无帧内 CPU/GPU 并行**——GPU 预处理完成后 P 核才开始，二者串行。并行性体现在**跨帧**（帧 k+1 的 GPU 预处理与帧 k 的 P 核计算重叠）。

### 4.3 关键设计决策

1. **不跳帧**：与扫描不同，标定姿态流水线**不丢弃帧**。每个采集周期都必须走完姿态判断，否则可能漏检目标姿态。若处理速度跟不上采集速度，环形缓冲会填满——此时**反压采集线程**（暂停写入，等待流水线消费），而非丢帧。

2. **GPU 单槽即可**：mask_extract + ccl 仅需 ~1-2ms，远短于 P 核标记点链（~10-20ms）。GPU 不会成为瓶颈，无需双槽或 MPS。

3. **PrevFrameState 用"最新快照"模型**：与扫描一致，`g_prevState` 全局原子指针，融合-01(2-12) 开始时 `load()` 最新快照，结束后 `store()` 发布。打破链式等待，X 个 E 核可同时算融合。

4. **姿态命中用原子 CAS 防重复**：多个流水线可能同时命中同一目标姿态。用 `atomic<bool> g_collected[25]` + CAS 操作，保证每个姿态仅被一个流水线标记。

5. **周期帧保存无锁**：每个姿态槽 `g_postureData[i]` 仅被成功 CAS 的那个流水线写入，天然无竞争。激光管帧在环形缓冲单元内随标记点帧一起传递。

## 5. P 核 Broker（动态租用）

**与扫描流水线完全相同**。E 核是编排线程（绑定 1 个 E 核），P 核工作由独立的 P 核 worker 线程池执行：X-1 个 worker，各绑 1 个 P 核。E 核提交标记点链任务到 worker 队列，在 future 上等。

### 待命轮转机制

X 个流水线，X-1 个 P 核 worker。任意时刻最多 X-1 个流水线在跑标记点链，1 个在别处（GPU/融合/预取）。

```
时刻 T 的快照（X=8）:
  流水线 0..6: RUN_PCORE (worker P1..P7)   ← 7 个 P 核全占用
  流水线 7:    已完成 ① PREFETCH + ② GPU 预处理，等 P 核  ← 待命

→ 流水线 0 标记点链跑完，进入 ④ 融合阶段（让出 P 核）
→ worker P1 空闲，从队列取下一个任务
→ 流水线 7 的任务被 P1 立即执行（无空窗）
```

---

## 6. E 核编排循环

E 核线程绑定 1 个 E 核，TIME_CRITICAL 优先级，循环执行：

1. **① PREFETCH**：从环形缓冲区 `grabNext()` 领取下一个采集周期单元。
2. **② GPU 预处理**：向 GPU Service 申请槽，跑 2-1 mask_extract + 2-2 ccl，释放槽。
3. **③ 标记点链**：提交 2-3~2-11 给 P-core Broker（拿 future）；`future.get()` 等 P 核完成（若全忙则阻塞 = 该流水线处于待命）。
4. **④ 单帧融合（E 核）**：`g_prevState.load()` 取最新快照；首帧走初始化分支；否则光流法融合，失败降级 `frame_fuse` 特征配准；产出后 `store()` 原子发布。
5. **⑤ 姿态判断（E 核）**：2-13 `pose_estimate` 输出姿态 (R,T)，与 25 个目标 4×4 矩阵逐一比对。命中且未采集 → CAS 标记 → 保存周期帧 → `g_collectedCount.fetch_add(1)`。
6. **⑥ DONE**：若 `g_collectedCount == 25` → 发出完成信号；否则回到 ①。

## 7. GPU 服务（1 槽）

### 7.1 职责

管理 1 个 CUDA stream 槽，提供 `acquireSlot / releaseSlot / stream()` 接口。用二值信号量（atomic + mutex + condition_variable）控制并发。E 核 acquire 时若槽忙则阻塞等待。

### 7.2 单槽依据

| 指标 | 扫描流水线 | 标定姿态流水线 |
|------|-----------|--------------|
| GPU 单帧工作量 | 预处理 + 激光 04~08（重） | mask + ccl（轻，~1-2ms） |
| GPU 槽数 | 2 | **1** |
| GPU 是否瓶颈 | 是 | **否** |

GPU 占用时间极短，单槽即可服务所有流水线。若实测 mask + ccl 耗时较高，可升级为双槽。

## 8. 环形缓冲区 + 反压策略

### 8.1 设计要点

- **单元**：`Cycle { id, markerL, markerR, laserFrames[], temperature, timestamp }`，整个采集周期打包为一个单元。
- **存储**：`atomic<shared_ptr<Cycle>>` 数组，槽位数 `N_SLOTS = 4 * X`。
- **写入**：P0 采集线程 `writePtr_` 单调递增写入。
- **读取**：各流水线用 `readCounter_` **顺序**领取帧号（不跳帧）。

### 8.2 反压逻辑（"不丢帧"语义）

与扫描的"抓最新跳中间帧"不同，标定姿态流水线**顺序消费每一帧**：

- 流水线领取帧号后正常处理。
- 若环形缓冲写满（`writePtr - maxReadCounter >= N_SLOTS`）：**采集线程阻塞**（暂停写入），等待流水线消费腾出空间。
- **不丢弃任何采集周期**——每个周期的标记点帧都必须经过姿态判断。

### 8.3 关键点

- **采集周期原子性**：标记点帧 + 激光管帧 + 温度在 `Cycle` 单元内，整单元读，无需额外同步。
- **shared_ptr 引用计数保活**：覆盖旧帧时，正在用的流水线仍持有引用。
- **激光管帧随单元传递**：流水线仅处理标记点帧，激光管帧作为"乘客"在单元内，姿态命中时一并保存。

## 9. PrevFrameState + 姿态采集集

### 9.1 PrevFrameState（与扫描一致）

`PrevFrameState`：上一帧标记点 `rawPoints`、`normals`、`globalIds`、位姿 `R_prev / T_prev`、来源帧号 `frameId`。全局 `std::atomic<std::shared_ptr<PrevFrameState>> g_prevState{nullptr}`。

读写协议：读（融合开始）`load()` 拿最新；写（融合结束）`store()` 原子覆盖。`shared_ptr` 引用计数保证安全。

### 9.2 姿态采集集（标定独有）

```cpp
// 25 个目标姿态的 4×4 变换矩阵（预计算，只读）
const cv::Matx44d g_targetPostures[25];

// 采集状态（原子操作）
std::atomic<bool> g_collected[25] = {};          // 各姿态是否已采集
std::atomic<int>  g_collectedCount{0};            // 已采集计数

// 保存的周期帧数据（每槽仅被一个流水线写入，无竞争）
struct PostureData {
    cv::Mat markerL, markerR;                     // 标记点帧
    std::vector<cv::Mat> laserFrames;              // 激光管帧
    double temperature;
    cv::Matx44d actualPosture;                     // 实际命中姿态
};
PostureData g_postureData[25];                     // 按姿态索引存储
```

### 9.3 姿态命中流程

```
2-13 输出姿态 (R,T)
    │
    ▼
遍历 25 个目标:
    计算与 g_targetPostures[i] 的平移差 ΔT + 角度差
    最佳匹配 i = argmin(距离)
    │
    ▼
距离 < 阈值 且 g_collected[i] == false?
    ├── 否 → 继续 (⑤结束, 回到 ①)
    └── 是 → CAS: g_collected[i].exchange(true)
              ├── CAS 失败 (已被其他流水线标记) → 继续
              └── CAS 成功 → 保存当前 Cycle 到 g_postureData[i]
                            → g_collectedCount.fetch_add(1)
                            → 若 count == 25 → g_completionFlag.store(true)
```

## 10. 全局状态与线程安全总表

| 状态 | 类型 | 访问者 | 同步方式 |
|------|------|--------|----------|
| 环形缓冲 `buf_[N_SLOTS]` | `atomic<shared_ptr<Cycle>>[]` | P0 写 / X 流水线读 | 原子 RMW + 引用计数 |
| `writePtr_` / `readCounter_` | `atomic<uint64>` | P0 / 流水线 | 原子 `fetch_add` |
| `g_prevState` | `atomic<shared_ptr<PrevFrameState>>` | X 个 E 核读写 | 原子 `load` / `store` |
| `g_targetPostures[25]` | `const Matx44d[]` | 所有 E 核只读 | 无需同步（初始化后不变） |
| `g_collected[25]` | `atomic<bool>[]` | X 个 E 核读写 | 原子 CAS |
| `g_collectedCount` | `atomic<int>` | X 个 E 核写 | 原子 `fetch_add` |
| `g_postureData[25]` | `PostureData[]` | 各槽仅 1 个 E 核写 | **无竞争**（CAS 保证唯一写入者） |
| P-core worker 队列 | `ConcurrentQueue<task>` | E 核 enqueue / worker dequeue | 无锁队列 |
| GPU 槽计数 | `atomic<int> + mutex + cv` | E 核 acquire/release | 信号量 |
| `g_completionFlag` | `atomic<bool>` | 1 个 E 核写 / 主线程读 | 原子 `store` / `load` |

**结论**：无硬串行点（标定姿态流水线无扫描的全局点云互斥融合）。所有共享状态均为原子或无竞争。

## 11. 性能分析

### 11.1 帧率估算

- 采集循环：标记点帧 + N 个激光管帧，总帧率 180fps
- 采集周期率 = 180 / (1+N)。若 N=4 → **36 周期/秒**
- 每周期需完成：GPU(~1-2ms) + P核标记点链(~10-20ms) + E核融合+姿态(~3-5ms)

### 11.2 瓶颈定位

| 资源 | 单帧占用 | 资源数 | 理论吞吐 | 是否瓶颈 |
|------|---------|--------|---------|---------|
| GPU | ~1-2ms | 1 槽 | ~500-1000 帧/秒 | 否 |
| P 核 | ~10-20ms | X-1=7 | ~350-700 帧/秒 | **是（上限最高）** |
| E 核 | ~3-5ms | X=8 | ~1600-2600 帧/秒 | 否 |

**瓶颈 = P 核标记点链**。但在 36 帧/秒的需求下，7 个 P 核提供 350+ 帧/秒的吞吐，远超需求。流水线**不会成为瓶颈**。

### 11.3 反压触发

若设备移动极慢、姿态变化平缓，大部分帧不会命中目标姿态。流水线持续 36 帧/秒处理，不会反压。仅在设备静止于某姿态附近时，帧率需求更低。

## 12. 启停与错误处理

### 12.1 启动顺序

1. 加载 25 个目标姿态 4×4 矩阵 → `g_targetPostures[25]`
2. 探测 CPU 拓扑（`GetLogicalProcessorInformationEx` + CPUID 0x1A）
3. 划分：P0（系统/采集）/ 流水线 P 核池 / 流水线 E 核
4. 创建 GPU Service（1 stream 槽）
5. 起 P-core Broker workers（X-1 个，各绑 P 核）
6. 起 X 个 E 核流水线线程
7. 启动 P0 采集线程（开始写环形缓冲，阶段 0 预热完成后开始）

### 12.2 错误处理

| 错误 | 处理 |
|------|------|
| 单帧标记点检测质量降级 | 仍提交融合（降级标记传入 PrevFrameState） |
| 融合失败（光流法匹配点 < 3） | 降级到 `frame_fuse` 特征配准；都失败则用上一帧 R/T |
| 姿态匹配失败（无目标在阈值内） | 正常情况，继续采集 |
| GPU kernel 失败 | 丢弃该帧标记点处理；激光管帧不保存（本周期无姿态命中） |
| 环形缓冲满 | **反压采集线程**（阻塞写入，等流水线消费） |

### 12.3 完成与停止

1. 某流水线检测到 `g_collectedCount == 25` → `g_completionFlag.store(true)`
2. 主线程检测到完成标志 → 停止 P0 采集
3. 等所有在飞帧完成（drain 环形缓冲）
4. 停 X 个 E 核流水线线程
5. 停 P-core Broker workers
6. 停 GPU Service
7. 收集 `g_postureData[25]` → 交付阶段 3（标记点帧）与阶段 4（激光管帧）

## 13. 设计约束与实现规范

1. **C++17 标准**（与现有代码一致；`atomic<shared_ptr>` 需 C++20 或退回 `atomic_load/store`）
2. **遵循现有算子的 pImpl 设计模式**
3. **使用 spdlog 日志**，遵循 `CALIB_LOG_*` 宏
4. **依赖限制**：仅 OpenCV、Eigen、CUDA；不引入 PCL；可选 moodycamel::ConcurrentQueue
5. **平台 API**：Windows `SetThreadAffinityMask`；跨平台抽象为 `ThreadAffinity` 接口
6. **与扫描流水线共享基础设施**：PCoreBroker、GpuService、RingBuffer 可复用同一套实现，仅配置参数不同（GPU 槽数 1 vs 2，单元类型 Cycle vs Frame，是否丢帧）

## 14. 开放问题

1. **N（激光管数）的实际值**：影响采集周期率和环形缓冲单元大小。当前假设 N=4，需确认设备实际激光管数（文档提及 17 或 25 条激光线，但激光管数 ≠ 激光线数）。
2. **姿态匹配阈值**：平移差 ΔT 和角度差的阈值需根据标定精度要求和实测数据确定。
3. **环形缓冲槽位数**：`N_SLOTS = 4 * X` 是否足够吸收抖动？在反压模式下，槽位数决定采集线程的最大等待时间。
4. **与扫描流水线的代码复用程度**：PCoreBroker / GpuService / RingBuffer 是否抽象为通用库，还是各模块独立实现。
