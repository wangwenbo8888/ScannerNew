# 三维扫描并行流水线调度设计文档（精简版）

> **基于 Intel CPU（X 个 P 核 + Y 个 E 核）+ NVIDIA GPU 的多流水线并行调度方案**
>
> 在 V2 单帧串行流水线之上增加硬件资源分配与跨帧并行调度层。**速度优先**。

---

## 1. 目标与约束

### 1.1 设计目标

在固定硬件资源下，最大化三维扫描流水线的吞吐量，充分利用每一个 P 核、E 核与 GPU SM。
流水线输出每帧的配准结果（R/T + 标记点3D + 激光3D点云），通过输出队列传递给下游消费者。

### 1.2 硬件约束（用户给定）

| 编号 | 约束 |
|------|------|
| C1 | 硬件为 Intel CPU（X 个 P 核 + Y 个 E 核）+ NVIDIA GPU |
| C2 | 1 个 P 核锁定给 Windows 系统 + 200fps 双目图像采集；同帧双目图打包为环形缓冲区的一个单元 |
| C3 | X-1 个 P 核 + X 个 E 核锁定给流水线；每流水线 = 1 P 核 + 1 E 核；E 核负责调度与汇合发布；这些核仅供流水线使用 |
| C4 | 流水线空闲时自动从环形缓冲区抓取**最新**图像 |
| C5 | 自动分配并行 X 个流水线；流水线数 = 分配给流水线的 P 核数 + 1（防 P 核空闲） |
| C6 | GPU 分配 2 个流水线（2 个并发槽）；扣除显示渲染与系统必须后，剩余 CUDA 核心平分给两个槽 |
| C7 | 速度优先 |

### 1.3 算法约束（来自既有算子设计）

| 编号 | 约束 | 影响 |
|------|------|------|
| A1 | `optical_flow_fuse` 依赖 `PrevFrameState`（上一帧标记点） | 配准需要前序帧信息 |
| A2 | 预处理-01 为唯一入口，ccl 输出区域标签是标记点链的启动条件 | ccl 完成后两链可并行 |
| A3 | 标记点链 03~11 + 配准全为 CPU 算子；激光链 04~08 全为 CUDA 算子 | 平台分布明确 |

## 3. 硬件资源分配

### 3.1 资源数学

| 资源 | 总数 | 分配 | 说明 |
|------|------|------|------|
| **P 核** | X | 1 → 系统/采集；**X-1 → 流水线 P 核池** | 动态租用 |
| **E 核** | Y (≥X) | **X → 流水线**（每流水线 1 个独占）；Y-X → 系统其它线程 | 静态绑定 |
| **GPU SM** | N_sm | `reservedSM` → 显示/系统；**剩余 (N_sm − reservedSM) / 2 → 每个 GPU 槽** | 双 stream 硬件自动调度 |
| **流水线数** | — | **X = (X-1) + 1** | 活跃 X-1 + 待命 1 |

### 3.2 实现方式

| 资源 | Windows API |
|------|-------------|
| 核心绑定 | `SetThreadAffinityMask` + `SetProcessPriorityClass` |
| 拓扑探测 | `GetLogicalProcessorInformationEx`（区分 P/E 核需读 CPUID 0x1A 叶子，或用 Intel TBB 的 `topology`） |
| P/E 核识别 | `hwloc` 库 或 `CPUID.0x1A.EAX[31:24]`（`CoreType`：0x20=Atom/E核，0x40=Core/P核） |
| GPU SM 平分 | 双 stream 硬件自动调度（单进程无需 MPS） |

### 3.3 关键不变量

- **E 核 ↔ 流水线**：1:1 静态绑定，**全生命周期不交换**
- **P 核 ↔ 流水线**：X 流水线竞争 X-1 P 核，由 P-core Broker 调度
- **GPU 槽 ↔ 流水线**：X 流水线竞争 2 槽，先到先得
- **流水线 X-1**：始终作为待命位，GPU 整链 + 预取提前完成，等 P 核释放即接管

## 4. 单帧生命周期与阶段分解

### 4.1 阶段状态机（E 核编排）

```
帧 N 生命周期：

状态                运行位置        算子                        等待条件
─────────────────────────────────────────────────────────────────────────
① PREFETCH          E核             (抓帧、组装输入)            环形缓冲有新帧
② WAIT_GPU          —               (排队)                      GPU 槽空
② RUN_GPU           GPU 槽A/B       ┌ 预处理-01 → 连通域分析    持槽串行，不释放
  │                                  │  (ccl 产出区域标签→供 P 核)
  │                                  │
  │                                  └ 激光04 → 05 → 06 → 07 → 08
  │                                     (steger→去畸变→极线插值
  │                                      →匹配→三维重建)
  │                 ┌───────────────┘
  │                 ▼  (ccl 就绪)
③ WAIT_PCORE        —               (GPU 激光链继续在后台跑)
③ RUN_PCORE         P核(动态)        标记点 03~11 → 配准
  │                                  (ccl 区域标签→image_split→
  │                                   Zernike→合并→去畸变→椭圆拟合
  │                                   →匹配→极线→边缘→三维重建
  │                                   →光流/快速配准)
  │                 ┌───────────────┐
  │                 │               │
  │              (P核链完成)     (GPU链完成)
  │              R/T+标记点3D    激光3D点云
  │                 └───────┬───────┘
  │                         ▼
④ PUBLISH           E核             汇合两边结果，组装 FrameResult
  │                                  → push 到输出队列
  │                                  (释放 GPU 槽，回到 ①)
```

### 4.2 阶段并行性

| 阶段 | 资源 | 帧内并行 | 跨帧并行 |
|------|------|----------|----------|
| ② GPU 整链 | GPU 槽 | ccl 完成后 **与 ③ 标记点链+配准完全并行** | 受 GPU 2 槽限制 |
| ③ 标记点链+配准 | P 核 | 与 ② GPU 链完全并行 | 受 X-1 P 核限制 |
| ④ 汇合发布 | E 核 | — | E 核并行（输出队列 push） |

### 4.3 关键设计决策

1. **GPU 链先产出 ccl，ccl 后两链完全并行**：GPU 预处理-01 产出掩膜后立即跑 ccl，ccl 的输出（区域标签+包围盒）是标记点链的启动条件。ccl 完成后 GPU 链继续串行跑激光 04~08（与 ccl 同 stream 串行是为了减少 stream 管理开销和保持 L2 亲和，ccl 和 steger 技术上无数据依赖——ccl 用 `d_markingPointMask`，steger 用 `d_laserMask`），P 核启动标记点链（`image_split` → … → `point_reconstruct` → `optical_flow_fuse`/`frame_fuse`）。此后两链互不依赖、完全并行，分别产出激光3D点云和 R/T+标记点3D。E 核等两边都完成后汇合发布。

2. **GPU 一个槽持槽串行，中间不释放**：`预处理 → 连通域 → 激光04~08` 在同一槽同一 stream 上串行跑完才释放。槽是全局瓶颈资源（仅 2 个），持槽串行保证 2 帧可同时推进。

3. **配准用"最新快照"模型，不严格等帧号 N-1**：`g_prevState` 由 P 核 worker 在配准时 `load()` 读取最新快照（可能跨几帧），完成后 `store()` 原子覆盖发布。**打破了链式等待**，X 个 P 核可同时算不同帧的配准。精度可忽略：200fps 下标记点帧间移动很小。

4. **E 核纯编排角色**：抓帧、申请 GPU 槽、派发 P 核任务、等两边完成、汇合发布。E 核不承担计算，始终不被阻塞在重计算上。

## 5. P 核 Broker（动态租用）

### 5.1 设计

E 核是编排线程（永久绑定 1 个 E 核），不能迁移到 P 核。P 核工作由**独立的 P 核 worker 线程池**执行：
X-1 个 worker，每个永久绑定 1 个 P 核（P1..P_{X-1}）。E 核提交任务到 worker 队列，在 future 上等。

**职责**：管理 X-1 个固定绑定 P 核的 worker 线程；接收 E 核提交的标记点链任务；轮询 / 队列分发；返回 future 供 E 核同步等待。Worker 空闲时 `yield` 让出。

### 5.2 待命轮转机制

**"+1"的本质**：X 个流水线，但只有 X-1 个 P 核 worker。任意时刻最多 X-1 个流水线在跑标记点链，
1 个在别处（等 GPU 槽/汇合发布）。这个"别处"的流水线就是事实上的待命位。

```
时刻 T 的快照（X=8）：
  流水线 0..6: RUN_PCORE (worker P1..P7)   ← 7 个 P 核全占用
  流水线 7:    已提交 GPU 整链（激光仍在后台跑），等 P 核  ← 待命

→ 流水线 0 标记点链跑完（已含配准），让出 P 核
→ worker P1 空闲，从队列取下一个任务
→ 流水线 7 的任务被 P1 立即执行（无空窗）
```

## 6. E 核编排循环

E 核线程固定绑定 1 个 E 核，TIME_CRITICAL 优先级，循环执行以下步骤：

1. **① PREFETCH**：从环形缓冲区 `grabLatest()` 抓最新帧。
2. **② GPU 整链**：向 GPU Service 申请槽，在槽内串行跑完整 GPU 链（预处理-01 → 连通域 → 激光04~08），**中间不释放槽**。ccl 完成后 E 核立即提交标记点链（含配准）到 P-core Broker，无需等激光链结束。
3. **③ 两边完全并行**：GPU 链和 P 核标记点链（含配准）帧内并行推进，互不依赖。E 核等 GPU 链 stream 完成（CUDA event 同步）和 `future.get()` P 核完成。
4. **④ 汇合发布**：两边都完成后，E 核组装 `FrameResult`（帧号、R/T、标记点3D、激光3D点云、温度），push 到输出队列；释放 GPU 槽；回到 ①。

## 7. GPU 服务（2 槽 + SM 平分）

### 7.1 职责

管理 2 个 CUDA stream 槽，提供 `acquireSlot / releaseSlot / stream(slot)` 接口；用计数信号量（atomic + mutex + condition_variable）控制并发；**先到先得**分配。E 核 acquire 时若无空槽则阻塞等待（可设超时兜底）。

### 7.2 SM 平分方案

| 方案 | 实现 | 优点 | 缺点 | 推荐度 |
|------|------|------|------|--------|
| **A. 双 stream 软限制** | 单进程 2 stream，靠 GPU 硬件调度 | 零配置、无额外依赖、按需动态均衡、GPU 利用率高 | 不保证硬性 50/50 | **推荐** |
| B. CUDA MPS | MPS daemon，2 client 各 `CUDA_MPS_ACTIVE_THREAD_PERCENTAGE=50` | 硬性 50/50 | 需起 daemon、部署复杂、空闲 SM 不能动态共享、daemon 崩溃影响全局 | 仅在**多进程**场景需要 |

### 7.3 帧内 GPU 工作串行

每帧占用一个槽，在槽内串行跑：
```
预处理-01 (mask separation) → 连通域分析 (markers only) → 激光04 → 激光05 → 激光06 → 激光07 → 激光08
```
**不在帧内让出槽**。2 个槽 = 同时服务 2 帧。

## 8. 环形缓冲区 + 丢帧策略

### 8.1 设计要点

- **单元**：`Frame { id, grayL, grayR, timestamp, temperature }`，双目同帧打包为一个单元。
- **存储**：`atomic<shared_ptr<Frame>>` 数组，槽位数 `N_SLOTS = 4 * X`（足够吸收抖动，内存可控）。
- **写入**：P0 采集线程 `writePtr_` 单调递增写入。
- **读取**：各流水线用 `readCounter_` 各自领取帧号。

### 8.2 抓帧逻辑（"抓最新"语义）

每个流水线从 `readCounter_` 领号后，计算落后量 `lag = writePtr_ − myFrameId`；若 `lag > DROP_THRESHOLD (= 2X)`，则跳到最新帧并推进读计数，丢弃中间帧；否则正常取自己领到的帧。

### 8.3 关键点

- **双目同帧原子性**：L 和 R 已在 `Frame` 单元内，整单元读，无需额外同步。
- **shared_ptr 引用计数保活**：捕获覆盖旧帧时，正在用的流水线仍持有引用，安全。
- **dropThreshold = 2X**：避免雪崩；高采集低处理时大部分帧会被跳过，但保证不延迟。

## 9. 输出队列

流水线配准完成后组装 `FrameResult { frameId, R, T, markerPoints3D, laserPoints3D, temperature }`，通过**无锁 MPMC 队列**（moodycamel::ConcurrentQueue）推送给下游消费者。队列容量 `N_SLOTS`（与环形缓冲对齐），满时最旧条目被覆盖（流水线侧非阻塞）。

下游消费者从队列异步 pop 消费，与流水线解耦。

## 10. PrevFrameState 原子快照

### 10.1 结构

`PrevFrameState` 包含：上一帧原始标记点 `rawPoints`、`normals`、`globalIds`、上帧位姿 `R_prev / T_prev`、来源帧号 `frameId`（诊断用）。全局持有 `std::atomic<std::shared_ptr<PrevFrameState>> g_prevState{nullptr}`。

### 10.2 读写协议

- **读**（配准时）：`load()` 拿当前最新，可能跨几帧。`nullptr` → 首帧初始化分支。
- **写**（配准结束时）：`store()` 原子覆盖发布本帧输出。旧快照由 shared_ptr 引用计数自动回收。

### 10.3 安全性

`shared_ptr` 引用计数保证：正在用旧快照的 P 核 worker 持有引用，覆盖不影响它。多个 P 核 worker 同时 load/store 是无锁且安全的（C++20 `std::atomic<std::shared_ptr>`；C++17 用 `std::atomic_load/store` 自由函数）。

## 11. 全局状态与线程安全总表

| 状态 | 类型 | 访问者 | 同步方式 |
|------|------|--------|----------|
| 环形缓冲 `buf_[N_SLOTS]` | `atomic<shared_ptr<Frame>>[]` | P0 写 / X 流水线读 | 原子 RMW + 引用计数 |
| `writePtr_` / `readCounter_` | `atomic<uint64>` | P0 / 流水线 | 原子 `fetch_add` / `store` |
| `g_prevState` | `atomic<shared_ptr<PrevFrameState>>` | P 核 worker 读写 | 原子 `load` / `store` |
| FrameResult 输出队列 | `ConcurrentQueue<FrameResult>` | E 核 push / 下游 pop | 无锁队列（moodycamel） |
| P-core worker 队列 | `ConcurrentQueue<task>` | E 核 enqueue / P-core worker dequeue | 无锁队列（moodycamel） |
| GPU 槽计数 | `atomic<int> + mutex + cv` | E 核 acquire/release | 信号量语义 |
| 全局统计（fps / 丢帧数） | `atomic<uint64>[]` | 所有线程 | 原子 |

**结论**：流水线内部无硬串行点。输出队列为无锁 MPMC，E 核 push 非阻塞。

## 12. 性能分析（定性）

- **瓶颈定位**：GPU 是唯一瓶颈。在半 SM（每槽半资源）下，单帧 GPU 串行工作量（预处理+连通域 + 激光 04~08）决定了流水线吞吐上限。
- **相对关系**：P 核池（X-1 个）处理标记点链+配准、E 核纯编排的能力均高于 GPU 吞吐；因此 GPU 2 槽是天花板。标记点数量异常多时 P 核可能成为次瓶颈。
- **丢帧**：相对 200fps 采集，处理吞吐不足部分以丢帧（跳最新）形式吸收，**保证不延迟**。
- **突破方向**：增加 GPU 槽数（用户固定为 2）或升级 GPU 才能提升流水线上限。

### 可选优化（超出本设计范围）

1. **GPU 槽数实测调优**：若 kernel 显存带宽受限（对 SM 数不敏感），2 槽×半 SM ≈ 1 槽×全 SM，需基准测试验证。
2. **帧内 GPU 流水化**：槽 A 跑帧 N 激光时，槽 B 跑帧 N+1 预处理，提升 GPU 占用率。
3. **标记点链 P 核子并行**：03~11 中按 ROI 并行拆分。

## 13. 启停与错误处理

### 13.1 启动顺序

1. 探测 CPU 拓扑（`GetLogicalProcessorInformationEx` + CPUID 0x1A）
2. 划分：P0（系统/采集）/ 流水线 P 核池 / 流水线 E 核
3. 创建 FrameResult 输出队列
4. 起 GPU Service（2 stream）
5. 起 P-core Broker workers（X-1 个，各绑 P 核）
6. 起 X 个 E 核流水线线程
7. 启动 P0 采集线程（开始写环形缓冲）

### 13.2 错误处理

| 错误 | 处理 |
|------|------|
| 单帧质量降级（QualityFlag::Degraded/Warning） | 仍发布到输出队列 |
| 配准失败（光流法匹配点 < 3） | 降级到 `frame_fuse`；都失败则用上一帧 R/T，仍发布 |
| GPU kernel 失败 | 丢弃整帧，不发布；流水线回 ① |
| GPU 槽 acquire 超时（kernel 卡死） | 丢弃整帧；标记 GPU Service 异常，触发全局降级 |
| 输出队列满 | 覆盖最旧条目（流水线侧非阻塞，不等待） |

### 13.3 停止顺序

1. 停 P0 采集
2. 等所有在飞帧完成（drain 环形缓冲）
3. 停 X 个 E 核流水线线程
4. 停 P-core Broker workers
5. 停 GPU Service
6. 释放资源

## 14. 设计约束与实现规范

1. **C++17 标准**（与现有代码一致；若用 `std::atomic<shared_ptr>` 需 C++20，或退回 `std::atomic_load/store`）
2. **遵循现有算子的 pImpl 设计模式**
3. **使用 spdlog 日志**，遵循 `CALIB_LOG_*` 宏
4. **QualityFlag 枚举**：所有阶段输出包含 qualityFlag
5. **依赖限制**：仅 OpenCV、Eigen、CUDA；不引入 PCL；可选用 moodycamel::ConcurrentQueue（header-only）
6. **平台 API**：Windows `SetThreadAffinityMask` 等；跨平台抽象为 `ThreadAffinity` 接口

## 15. 与单帧算子流程的关系

本设计**不替代**单帧算子流程，而是在其之上增加调度层：

| 单帧算子流程 | 本并行调度层 |
|---------------|--------------|
| 定义单帧内算子的执行顺序与数据流 | 定义跨帧的并行调度与资源分配 |
| `mask_separation` / `optical_flow_fuse` 等核心算子 | 复用算子定义，仅改变调度方式 |
| 每帧顺序执行 | X 帧并行 + 阶段内并行 |

**实现路径**：
1. 所有核心算子已实现（`core/` + `scanning/`），在此基础上增加调度层
2. 实现调度层（PCoreBroker、GpuService、RingBuffer、OutputQueue、Pipeline 编排器）
